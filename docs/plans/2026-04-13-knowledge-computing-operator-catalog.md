# 知识计算算子目录重定方案

**日期**: 2026-04-13

## 1. 目的

基于以下两份清单，重新确定后续“知识计算工作台”的统一算子目录和实施边界：

- [知识计算算子清单（适配KAG规范+自定义业务框架版）](/Users/caixudong/Downloads/zhilian-robot/知识计算算子清单（适配KAG规范+自定义业务框架版）.docx)
- [知识计算算子清单（增加业务扩展）](/Users/caixudong/Downloads/zhilian-robot/知识计算算子清单（增加业务扩展）.docx)

本方案的目标不是立即重写现有实现，而是先把后续统一实现时要遵循的**顶层分类、扩展维度、代码结合方式**定清楚。

---

## 2. 结论

后续算子目录不再沿用当前工作台中的 6 层偏实现型分类，而统一采用如下 7 类“知识计算”顶层目录：

1. 数据接入与加载
2. 数据预处理与结构化
3. 知识抽取
4. 知识对齐与标准化
5. 知识融合与图构建
6. 知识检索与召回
7. 推理与决策生成

同时，把“通用基础算子 / 业务扩展算子”作为**第二维分类**，而不是顶层目录的一部分。

这意味着后续每个算子都至少有两层归属：

- 一层是它属于哪一类知识计算能力
- 一层是它属于通用能力还是产业研究分析等业务扩展能力

---

## 3. 为什么要改

当前工作台里的 6 层分类更偏实现路径：

- 原始接入层
- 解析标准化层
- 结构整理层
- 知识抽取层
- 映射建图层
- 融合归一层

这套分类对当前开发和前端展示是够用的，但它有三个明显问题：

1. 更像“实现流水线分段”，不是“知识计算能力目录”
2. 没有显式容纳检索、推理、报告生成等后续能力
3. 难以同时承接 `KAG` 通用算子和产业研究分析的业务扩展算子

而你提供的两份清单已经给出了更完整的能力版图，尤其第二份清单已经明显超出了单纯知识抽取和图谱落图，进入了：

- 检索
- 推理
- 预警
- 评估
- 自动化生成

所以顶层目录必须上收，变成“知识计算能力目录”。

---

## 4. 新的顶层目录

### 4.1 数据接入与加载

职责：

- 接入 PDF、网页、Markdown、Word、RSS、结构化表、数据仓库等来源
- 统一形成标准源对象

典型算子：

- PDF 数据加载
- 网页数据加载
- RSS 资讯加载
- 结构化专题数据加载
- 产业链专题数据加载
- 政策法规专项加载
- 科创成果专项加载

这一层的核心是“接进来”，不负责深度理解。

### 4.2 数据预处理与结构化

职责：

- 文档解析
- 文本清洗
- 标准化
- 切块
- 提纲识别
- 表格结构化

典型算子：

- PDF 解析
- HTML 正文抽取
- Markdown 规范化
- 文档清洗
- 专利全文预处理
- 政策文本标准化
- 企业公告清洗标准化
- 产业分类代码标准化
- Chunk 切分
- 表格抽取

这一层的核心是把不同原始数据整理成“适合知识计算的标准中间对象”。

### 4.3 知识抽取

职责：

- 从标准中间对象中抽出实体、关系、事件、概念种子、表格事实等

典型算子：

- 实体抽取
- 关系抽取
- 事件抽取
- 实体标准化
- 概念种子抽取
- 表格事实抽取
- 产业政策要素抽取
- 专利核心要素抽取
- 产业链上下游关系抽取
- 企业科创能力要素抽取
- 投融资事件抽取
- 人才核心要素抽取
- 产业风险事件抽取

这一层的核心是“把知识抽出来”，但还不对齐、不融合。

### 4.4 知识对齐与标准化

职责：

- 把不同来源抽出的知识统一到标准实体、标准概念、标准术语和标准层级上

典型算子：

- 企业实体归一化
- 技术术语标准对齐
- 产业标准分类对齐
- 政策条款层级对齐
- 地区标准化
- 时间标准化
- 编码标准化

这一层和知识抽取分开很重要。抽取是“发现候选知识”，对齐是“把候选知识变成统一知识对象”。

### 4.5 知识融合与图构建

职责：

- 多源知识融合
- 子图构建
- 图导入
- 时效性更新
- 合规性校验

典型算子：

- 多源企业数据融合
- 产业链知识图谱融合
- IPC-ICD 双链融合
- 知识图子图组装
- 图谱批次构建
- 图谱导入
- 产业知识时效性更新
- 产业知识合规性校验

这一层的核心是“变成统一可用的大图”。

### 4.6 知识检索与召回

职责：

- 基于实体、概念、关系、向量、专题视角做知识检索与召回

典型算子：

- 产业链专题检索
- 政策精准匹配检索
- 专利技术相似性检索
- 企业全景信息检索
- 招商资源智能匹配检索

这一层虽然不一定在首批实现，但必须成为目录中的一等能力，而不是工作台之外的旁路功能。

### 4.7 推理与决策生成

职责：

- 基于知识图谱、概念层、规则和检索结果做推理、评估、预警和自动生成

典型算子：

- 产业链链路推理
- 企业科创能力评估推理
- 政策-企业精准匹配推理
- 招商资源智能匹配推理
- 企业供应链风险预警推理
- 专利技术价值评估推理
- 产业发展态势预测推理
- 投融资标的价值评估推理
- 智能报告自动化生成

这一层对应的是“知识计算”的真正上层价值。

## 5. 第二维分类

顶层目录确定后，每个算子再按第二维做归属：

### 5.1 通用基础算子

特点：

- 与具体行业弱耦合
- 更接近 `KAG`、`DataFlow`、通用文档处理和通用图构建能力
- 可在多个业务领域复用

例如：

- PDF 解析
- 文档清洗
- 切块
- 实体抽取
- 关系抽取
- 结构化映射
- 图导入

### 5.2 业务扩展算子

特点：

- 与产业研究分析业务强耦合
- 和政策、产业链、专利、人才、招商、投融资等主题直接相关
- 需要行业规则、术语体系、业务 schema 和推理逻辑

例如：

- 产业链上下游关系抽取
- 政策精准匹配推理
- 企业供应链风险预警推理
- 招商资源智能匹配检索
- 企业科创能力评估推理

推荐在工作台中把这两个维度同时展示：

- 第一维：能力层级
- 第二维：通用 / 业务扩展

## 6. 与当前实现的对应关系

### 6.1 当前 6 层实现是“过渡目录”

当前代码里的目录定义在 [catalog_specs.py](/Users/caixudong/Downloads/zhilian-robot/backend/app/knowledge_extraction_operators/catalog_specs.py)：

- `source_ingest`
- `document_parse`
- `structure`
- `extract`
- `mapping`
- `fusion`

这套定义保留为当前前端工作台和后端接口的实现目录没有问题，但后续应视为**过渡版**。

### 6.2 后续映射关系

建议映射如下：

- `source_ingest` -> 数据接入与加载
- `document_parse` + `structure` -> 数据预处理与结构化
- `extract` -> 知识抽取
- 当前缺失的新层 -> 知识对齐与标准化
- `mapping` + `fusion` -> 知识融合与图构建
- 当前缺失的新层 -> 知识检索与召回
- 当前缺失的新层 -> 推理与决策生成

也就是说，后续不是完全推翻现有实现，而是把现有实现重定位到新的目录中。

## 7. 与 KAG 和 OpenSPG 的结合方式

## 7.1 先明确三层职责

### KAG

定位：

- 通用知识构建引擎
- 提供 `reader / splitter / extractor / mapping / writer`
- 擅长结构化映射和 schema 约束抽取

### OpenSPG

定位：

- schema
- 图谱存储
- 图谱服务
- 图谱查询与推理基础设施

### 我们自己的知识计算算子层

定位：

- 统一算子目录
- DTO
- registry
- pipeline 编排
- 业务扩展算子
- 前端工作台
- 试跑、校验、执行、保存

结论：

`KAG` 和 `OpenSPG` 都不应该直接承担“知识计算算子平台”的产品层职责。

---

## 7.2 三种实现路径对比

### 路径 A：直接基于 KAG 拉业务分支扩展

做法：

- 在当前 `modules/kag` 上直接拉业务分支
- 通用能力和业务算子都改进到 KAG 代码里

优点：

- 组件就地改
- 与 `KAG` 内部耦合最紧

问题：

- 后续升级上游 `KAG` 成本高
- 业务算子会污染通用能力边界
- 工作台、DTO、agent 编排等平台逻辑也会被迫挤进 KAG

判断：

不建议作为主路径。

### 路径 B：另起一个独立新库，import KAG

做法：

- 新建独立仓库
- 通过 pip 包或源码方式引入 `KAG`
- 在新库里做知识计算算子框架

优点：

- 边界干净
- 理论上最清晰

问题：

- 现在会带来额外仓库、版本、发布和联调成本
- 当前项目内已经有大量与 `KAG/OpenSPG` 耦合的业务实现，马上拆库不划算

判断：

可以作为远期演进方向，但不适合作为当前阶段主路径。

### 路径 C：在当前仓库内建立知识计算算子层，包装 KAG

做法：

- 保持 `modules/kag` 作为上游引擎层
- 在当前仓库内独立维护知识计算算子层
- 用包装器方式复用 `KAG` 组件
- 同时接入我们自己的业务扩展算子

优点：

- 工程成本最低
- 兼容当前已有实现
- 后续要拆库也不难
- 不阻断 `KAG` 升级

判断：

**这是当前阶段的推荐方案。**

## 7.3 推荐的代码组织方式

建议采用以下结构：

- `modules/kag`
  - 保持为引擎层和通用组件层
- `backend/app/knowledge_extraction_operators`
  - 后续逐步演化为“知识计算算子层”
  - 负责 operator spec、DTO、registry、runtime、front workbench API
- `backend/app/incore_fusion_pipeline`
  - 保持为现有融合归一和图构建业务实现
- `frontend/src/.../operator-workbench`
  - 作为知识计算工作台的产品层入口

后续更合理的方向是：

- 保留包路径兼容一段时间
- 对外产品命名统一改成“知识计算”
- 内部代码可以分阶段从 `knowledge_extraction_operators` 演进到 `knowledge_computing_operators`

这比一次性大改路径更稳。

## 8. 对后续实现的约束

后续新增算子时，必须遵守以下约束：

1. 新增算子必须先归属到 7 类顶层目录之一
2. 每个算子必须标注是通用基础还是业务扩展
3. 能直接复用 `KAG` 的，优先包装，不重复造轮子
4. 业务扩展算子只放在我们自己的算子层，不直接改写进 `KAG`
5. `OpenSPG` 只负责 schema 和图服务，不承担工作台逻辑
