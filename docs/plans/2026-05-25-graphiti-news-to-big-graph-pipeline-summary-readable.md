# Graphiti 资讯接入大图链路说明

## 1. 我们这次在做什么

我们这次主要做的是一件事：把 Graphiti 收集和抽取出来的资讯知识，接到我们已经构建好的产业网链大图里。

这里的大图可以理解成两层：

- 第一层是比较稳定的“常识底座”，主要来自 Wikidata，例如企业、产品、技术等基础信息。
- 第二层是不断更新的“资讯动态”，来自 RSS、八爪鱼、网页等资讯源，例如企业的新动作、产品变化、市场事件、供应链变化等。

这两类数据的更新频率不同。Wikidata 这类常识数据可以较长时间保持不变，但资讯数据会频繁更新。如果我们把资讯里的动态字段直接写进常识节点里，后续就很难维护，也很难判断哪些内容是长期事实，哪些只是某一篇资讯里的临时信息。

所以我们采用的做法是：常识节点不被资讯直接覆盖，资讯抽取出来的内容先形成自己的动态节点，再通过关系挂到常识节点上。

简单说，就是：

```text
Wikidata 负责提供稳定骨架
Graphiti 负责从资讯里抽取动态事实
融合层负责把动态事实挂到稳定骨架上
```

## 2. 为什么不能直接把资讯合并到 Wikidata 节点里

例如 Wikidata 里已经有一个“三星集团”节点，它是我们常识大图里的企业节点。

如果一篇资讯说“三星集团存储芯片价格变化”，我们不应该直接把这篇资讯里的所有内容都写进“三星集团”这个常识节点。原因是：

- 资讯是高频更新的，今天有一篇，明天还会有很多篇。
- 资讯内容有时效性，很多信息只在某个时间点成立。
- 如果直接覆盖常识节点，会让常识层变得混乱。
- 后续删除、更新、回溯某一篇资讯来源会变得困难。

因此我们采用“链接”的方式：

```text
资讯中抽取出的“三星集团”动态画像
-> 指向
Wikidata 中的“三星集团”常识节点
```

这样既能保留资讯里的动态信息，又不会破坏常识图谱的稳定性。

## 3. 改造后的整体流程

现在的流程可以理解为 6 步。

### 第一步：收集资讯

Graphiti 资讯项目会从 RSS、八爪鱼、网页等来源获取资讯数据。

这些数据最开始只是普通文本，例如一篇新闻、一条快讯或一段网页内容。

### 第二步：清洗和压缩资讯

拿到资讯后，系统会先做基础处理：

- 去掉无关内容。
- 判断是否和产业知识相关。
- 去重，避免重复处理同一篇资讯。
- 把长文本压缩成更适合知识抽取的文本。

这一步的目标是把原始资讯变成适合 Graphiti 抽取的输入。

### 第三步：Graphiti 抽取知识

处理后的资讯会被送到 Graphiti。

Graphiti 会从文本里抽取：

- 资讯节点，也就是这篇资讯本身。
- 实体节点，例如企业、产品、技术、行业等。
- 关系，例如“企业提到了某个产品”“某个产品受到需求增长影响”等。

抽取完成后，这些节点和关系会先写入 Graphiti 自己的 Neo4j 图数据库。

### 第四步：按批次读取 Graphiti 抽取结果

这是本次改造中很重要的一点。

每次资讯收集任务都会生成一个运行编号，也就是 `run_id`。我们现在把这个 `run_id` 传给 Graphiti，作为本次抽取的批次标识。

这样后续融合时，系统就知道应该只读取“本次资讯任务”的抽取结果，而不是把 Graphiti 历史上所有资讯节点都读进来。

这解决了一个很关键的问题：避免把旧数据、历史测试数据、其他批次数据误融合进当前大图。

### 第五步：和 Wikidata 常识节点做匹配

融合层会拿 Graphiti 抽取出的实体去和 Wikidata 常识图里的节点做匹配。

例如 Graphiti 从资讯里抽取出：

```text
三星集团
三星电子
固态硬盘
DRAM
NAND闪存
```

系统会尝试判断这些实体是不是已经存在于 Wikidata 常识图中。

如果匹配成功，就生成一个动态资讯画像节点，并通过 `refersTo` 指向 Wikidata 节点。

如果匹配不成功，就保留为资讯侧新增节点，后续可以继续补充匹配规则。

### 第六步：写入主图

最后，融合结果会被写入我们的 OpenSPG Neo4j 主图中。

写入后，主图里就不只有稳定的 Wikidata 常识节点，也有从资讯中抽取出来的动态事实节点和动态关系。

## 4. 融合后的图长什么样

融合后不是把所有内容合并成一个节点，而是形成一种“常识骨架 + 动态挂接”的结构。

例如资讯里提到了“三星集团”，并且系统识别到它对应 Wikidata 中的三星集团节点，那么图里会形成：

```text
NewsEntityProfile:graphiti:xxx
-> refersTo
Enterprise:wiki:Q20716
```

可以把它理解成：

```text
资讯侧的三星集团画像
-> 指向
常识图里的三星集团节点
```

如果资讯里出现了一个暂时无法匹配到 Wikidata 的实体，比如某个产品或技术词，系统会先保留它：

```text
Product:fusion:graphiti:xxx
Technology:fusion:graphiti:xxx
```

这样不会丢失信息，后续可以继续完善匹配规则。

## 5. 本次具体改了哪些能力

### 5.1 增加了批次标识

以前 Graphiti 抽取出的节点没有稳定的批次边界。融合时如果直接读取 Graphiti 图，就容易读到历史数据。

现在我们把 crawler 的 `run_id` 贯穿到 Graphiti 抽取和主图融合中。

也就是说，每一次资讯任务都有自己的批次号。后续融合时，只融合这个批次的数据。

### 5.2 让 Graphiti 抽取结果可以按批次进入主图

我们增强了 Graphiti 到主图的读取逻辑。

现在系统会按 `group_id` 读取 Graphiti 中对应批次的资讯节点和实体节点，并把相关关系一起取出来。

这样可以保证：

- 本次任务的数据不会和历史数据混在一起。
- 本次资讯中提到的关联实体不会丢失。
- 后续可以按批次追踪和排查问题。

### 5.3 增加了一键融合入口

我们增强了融合脚本，让它可以承担完整流程编排。

现在它可以做这些事：

- 检查 Graphiti 服务是否可用。
- 初始化 Graphiti 图数据库。
- 可选执行资讯采集任务。
- 读取本次任务的 Graphiti 抽取结果。
- 和 Wikidata 常识图做匹配。
- 生成融合结果。
- 写入 OpenSPG Neo4j 主图。
- 输出本次运行报告。

这让整个链路从“几个分散能力”变成了一条可以重复执行的 pipeline。

## 6. 每次运行会生成什么结果

每次运行后，会生成一组文件，方便检查和追溯。

主要有 4 个：

- `fusion_batch.json`：最终准备写入主图的节点和关系。
- `node_decisions.json`：每个节点是匹配到了 Wikidata，还是作为新节点创建。
- `relation_decisions.json`：每条关系是怎么映射到主图里的。
- `fusion_report.json`：本次运行的总体报告，包括节点数、边数、批次号、warning 等。

这些文件的作用是让我们知道：

- 这次到底融合了多少数据。
- 哪些实体匹配到了已有常识节点。
- 哪些实体没有匹配上。
- 哪些关系被写进了主图。
- 如果有问题，应该从哪里排查。
