# 产业⽹链⼤知识存储设计⽂档

# ⼀、 引⾔

# 1.1 设计背景

产业⽹链⼤知识存储核⼼⽀撑产业数据的结构化沉淀、关联挖掘与⾼效复⽤，需整合“资源-内容-实体-事实-上下⽂”全链路数据。本设计聚焦知识⽹络核⼼的五张⼤表（标准化⽂档表、微内容表、实体表、事实表、上下⽂表），采⽤窄表设计思想并参照Newsreader规范，实现数据轻量存储、⾼效查询与全链路溯源。

# 1.2核⼼⽬标

• 结构化存储产业⽹链核⼼知识要素，明确五张⼤表的职责边界与关联逻辑；

• 践⾏窄表设计理念，精简冗余字段，提升数据写⼊与查询的⾼吞吐能⼒；

• 参照Newsreader规范，保障实体、事实、上下⽂的层间分离与规范关联；

• 构建全链路溯源体系，确保知识数据的真实性、可追溯性与质量可控。

# 1.3 适⽤范围

本设计适⽤于产业⽹链⼤知识存储系统的核⼼数据层构建，涵盖数据要素的抽取、存储、关联、查询全流程，为上层知识服务、数据分析、语义检索等应⽤提供⽀撑。

# ⼆、整体设计原则

窄表核⼼原则：每张表聚焦单⼀核⼼职责，仅存储必要字段，冗余信息通过关联表反向获取，降低存储开销与IO压⼒；

• 层间分离原则：参照Newsreader“资源-提及-实体-陈述-上下⽂”层间分离逻辑，明确五张⼤表的层级定位，避免功能重叠；

唯⼀标识原则：所有表均采⽤全局唯⼀ID关联，确保表间关联的精准性与可追溯性；

⾼效查询原则：针对核⼼查询场景设计精准索引，覆盖“实体-属性/关系”“⽂档-事实”“事实-溯源”等⾼频场景；

兼容性原则：字段设计兼容产业⽹链多类型数据（新闻、报告、政策等），⽀持后续数据扩展与功能迭代。

# 三、核⼼五⼤表详细设计

产业⽹链⼤知识存储的五张⼤表构成“数据资源-内容⽚段-知识实体-事实关联-上下⽂补充”的完整知识链路，各表职责与设计细节如下：

# 3.1 标准化⽂档表（lnc_document）⸺资源层核⼼载体

# 3.1.1 设计定位

作为知识抽取的基础数据载体，存储经过标准化处理的产业相关⽂档（新闻、政策、⾏业报告等），为微内容抽取与事实提取提供原始数据源，同时记录⽂档核⼼属性与来源基础信息。

# 3.1.2 字段结构

Code block

```json
1 {   
2 "_id": ObjectId("..."),   
3 "doc_id": "DOC_NEWS_BAIDU_20260130_0001", // 全局唯一ID，格式：DOC_<资源类型><来源><日期><序号>   
4 "resource_doc_id": "DOC_NEWS_BAIDU_20260130_0001", // 关联资源层原始文档ID，支撑溯源   
5 "resource_file_id": "4f8a4c7b1f2b9e3b0a0b5d3f5f1e9c2a9e0d7b3a", // 关联资源层文件ID（如有附件）   
6 "title": "2026年新能源产业政策解读", // 标准化后文档标题   
7 "standard_content": "全文标准化内容...", // 清洗、去重、格式标准化后的文档正文   
8 "summary": "文档核心摘要...", // 文档语义摘要，支撑快速检索   
9 "resource_type": "news", // 资源类型：news/policy/report/company_profile   
10 "data_source": "baidu", // 数据来源：baidu/sina/ths/enterprise_official   
11 "language": "zh-CN", // 语言类型：zh-CN/en   
12 "publish_time": ISODate("2026-01-30T09:00:00Z"), // 标准化发布时间   
13 "source_info": { // 基础来源信息   
14 "ds_id": "DS_NEWS_BAIDU_001", // 数据源ID   
15 "source_url": "https://news.baidu.com/xxx", // 原始来源URL   
16 "credibility_score": 90.0 // 来源可信度评分 (0-100)   
17 },   
18 "ontology_class_id": "OC000000000001", // 关联本体类ID，标记文档所属语义类别   
19 "tags": ["新能源", "产业政策"], // 语义标签，支撑分类检索   
20 "embedding": [0.12, -0.34, ..., 0.89], // 文档语义向量（可选，支撑向量检索）   
21 "model_version": "bge-m3-v1", // 向量生成模型版本   
22 "status": "active", // 状态：active/deprecated（有效/废弃）   
23 "process_batch_id": "BATCH_20260130_001", // 加工批次ID，支撑批量处理   
24 "created_at": ISODate("2026-01-30T10:00:00Z"), // 存储创建时间   
25 "updated_at": ISODate("2026-01-30T10:00:00Z") // 最后更新时间   
26 }
```

# 3.1.3 关键说明

• 标准化核⼼：对原始⽂档的标题、正⽂进⾏格式清洗与语义标准化，确保数据⼀致性；

• 基础溯源：通过resource_doc_id、source_info关联资源层原始数据，保障⽂档来源可查；

• 语义增强：通过ontology_class_id、tags、embedding实现⽂档的语义结构化，⽀撑精准检索。

# 3.1.4 索引设计

• 唯⼀索引：doc_id（全局唯⼀，核⼼关联标识）、resource_doc_id（关联资源层唯⼀标识）；

• 查询索引：resource_type+data_source（按类型+来源筛选查询）、publish_time（按时间范围查询）；

• 语义检索索引：ontology_class_id、tags（⽀持分类检索）。

# 3.2 微内容表（lnc_microcontent）⸺ 提及层核⼼载体

# 3.2.1 设计定位

存储从标准化⽂档中抽取的精准语义⽚段（句⼦、短语、关键词等），作为事实提取的直接证据来源，仅通过doc_id与⽂档强关联，践⾏窄表设计理念，不冗余存储⽂档其他信息。

# 3.2.2 字段结构

```txt
Code block  
1 {  
2 "_id": ObjectId("..."),  
3 "microcontent_id": "MC_DOC_NEWS_BAIDU_20260130_0001_001", // 全局唯一ID，格式：MC_<关联doc_id>_<序号>  
4 "doc_id": "DOC_NEWS_BAIDU_20260130_0001", // 唯一关联字段，关联lnc_doc.doc_id  
5 "content_type": "sentence", // 微内容类型：sentence/phrase/keyword/table_cell  
6 "content": "2026年将加大新能源产业补贴力度", // 微内容核心文本  
7 "source_position": { // 文档内精准位置，支撑证据溯源  
8 "start_char": 100, // 正文起始字符位置  
9 "end_char": 150, // 正文结束字符位置  
10 "page": 1 // 页码（如有分页文档）  
11 },  
12 "ontology_property_id": "OP000000000001", // 关联本体属性ID，标记微内容语义属性  
13 "embedding": [0.45, 0.23, ..., 0.67], // 微内容语义向量（可选）  
14 "model_version": "bge-m3-v1", // 向量生成模型版本  
15 "confidence": 0.98, // 微内容语义可信度（θ-1）  
16 "status": "active", // 状态：active/deprecated  
17 "process_batch_id": "BATCH_20260130_001", // 加工批次ID  
18 "created_at": ISODate("2026-01-30T10:30:00Z"),  
19 "updated_at": ISODate("2026-01-30T10:30:00Z")  
20 }
```

# 3.2.3 关键说明

• 窄表精简：仅保留与微内容⾃⾝相关的核⼼字段，⽂档关联仅依赖doc_id，避免信息冗余；

• 证据精准性：通过source_position记录⽂档内精准位置，确保后续事实提取的证据可定位；

语义关联：通过ontology_property_id关联本体，为后续事实提取的语义匹配提供⽀撑。

# 3.2.4 索引设计

• 唯⼀索引：microcontent_id（全局唯⼀标识）；

• 核⼼关联索引：doc_id（单字段索引，⽀撑“⽂档-微内容”快速关联查询）；

• 筛选索引：content_type+ontology_property_id（按类型+语义属性筛选查询）、process_batch_id+status（批量加⼯状态查询）。

# 3.3 实体表（lnc_entity） ⸺实体层核⼼载体

# 3.3.1 设计定位

参照Newsreader实体层规范，聚焦实体核⼼标识与类型，仅存储实体基础信息，不冗余存储实体属性与来源信息，实体属性通过关联事实表获取，实现实体表的极致精简。

# 3.3.2 字段结构

Code block

```json
1 {   
2 "_id": ObjectId("..."),   
3 "entity_id": "EN0000000000000001", // 全局唯一URI，兼容Newsreader实体URI规范，格式：EN_<序号>   
4 "class_id": "OC0000000000002", // 关联本体类ID，标记实体类型（如“企业”“产品”“政策”)   
5 "name": "XX新能源科技有限公司", // 实体标准名称   
6 "name_en": "XX New Energy Technology Co., Ltd.", // 英文名（如有，支撑国际化）   
7 "aliases": ["XX新能", "XX科技"], // 实体别名，对应Newsreader提及层的多名称映射   
8 "status": "active", // 状态：active/deprecated   
9 "created_at": ISODate("2026-01-30T11:00:00Z"),   
10 "updated_at": ISODate("2026-01-30T11:00:00Z")   
11 }
```

# 3.3.3 关键说明

层间分离：严格遵循Newsreader实体层与陈述层分离原则，实体属性不存储于实体表，通过关联事实表获取，确保职责单⼀；

• 标识统⼀：entity_id采⽤URI格式，兼容Newsreader规范，⽀撑后续跨系统知识融合；

. 多名称适配：通过aliases存储实体别名，匹配⽂档中不同名称的提及，提升实体关联准确率。

# 3.3.4 索引设计

• 唯⼀索引：entity_id（全局唯⼀，核⼼关联标识）；

• 查询索引：name（单字段索引，⽀撑实体名称精准查询）、class_id（按实体类型筛选查询）、aliases（别名模糊查询索引）。

# 3.4 事实表（lnc_statement）⸺ 陈述层核⼼载体

# 3.4.1 设计定位

参照Newsreader陈述层�subject, predicate, object, context�核⼼模型，践⾏窄表设计思想，仅存储事实三元组核⼼信息与context_id关联字段，所有溯源、证据信息均通过context_id反向关联上下⽂表获取。

# 3.4.2 字段结构

```txt
Code block  
1 {  
2 "_id": ObjectId("..."),  
3 "statement_id": "ST_0000000000000001", // 全局唯一URI，兼容Newsreader陈述URI规范，格式：ST_<序号>  
4 "subject_id": "EN0000000000000001", // 主体实体ID，关联lnc-entity（对应Newsreader subject)  
5 "predicate_id": "RT00000000000001", // 谓词ID，关联本体关系/属性（对应Newsreader predicate)  
6 "object_type": "entity|literal", // 对象类型：实体（关系型事实）/字面量（属性型事实）  
7 "object_id": "EN0000000000000002", // 客体实体ID（仅object_type=entity时存在）  
8 "object_value": "1000万元", // 客体字面量值（仅object_type=literal时存在，如注册资本、成立时间）  
9 "context_id": "KC_0000000000000001", // 核心关联字段，关联lnc_context获取溯源信息  
10 "confidence": 0.96, // 事实置信度（θ-1，Newsreader陈述置信度元数据）  
11 "crystallized": false, // 结晶标识（参照Newsreader，标记是否为背景知识）  
12 "status": "active", // 事实状态：active/deprecated  
13 "process_batch_id": "BATCH_20260130_001", // 加工批次ID  
14 "created_at": ISODate("2026-01-30T11:30:00Z"),  
15 "updated_at": ISODate("2026-01-30T11:30:00Z")  
16 }
```

# 3.4.3 关键说明

• 三元组核⼼：严格遵循�subject, predicate, object�核⼼模型，清晰表达“主体-关系/属性-客体”的事实逻辑；

• 窄表极致：移除所有可通过关联获取的冗余信息，仅保留事实核⼼标识与关联字段，单条记录轻量化；

• 幂等保障：可通过statement_id的URI唯⼀性或基于“subject_id+predicate_id+object_type+object_id/object_value”⽣成的hash值，确保事实不重复插⼊；

背景知识标记：crystallized字段标记事实是否为结晶化背景知识，⽀撑后续知识融合逻辑。

# 3.4.4 索引设计

• 唯⼀索引：statement_id（全局唯⼀标识）；

• 核⼼关联索引：context_id（单字段索引，⽀撑与上下⽂表快速关联）；

. 事实查询索引：subject_id+predicate_id+object_type（复合索引，覆盖“实体-属性/关系”核⼼查询场景）；

批量处理索引：process_batch_id+status（复合索引，⽀撑批量加⼯与状态更新）。
