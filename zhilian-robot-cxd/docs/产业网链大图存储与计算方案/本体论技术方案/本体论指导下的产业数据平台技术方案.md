# 本体论指导下的产业数据平台技术方案

## 一、背景与挑战

### 1.1 背景与挑战

公司当前数据平台（天蓬大数据平台）已具备完善的数据接入、存储、处理、服务能力，但面临以下挑战：

| 挑战维度 | 具体表现 |
|----------|----------|
| **数据孤岛** | 多种数据库混用（MySQL、MongoDB、ES、Doris），数据分散，关联分析困难 |
| **关联深度不足** | 传统关系型数据库难以支撑6层以上的股权穿透、供应链追溯等深度关联查询 |
| **语义缺失** | 数据仅存储事实，缺乏对业务语义与操作边界的定义 |
| **AI幻觉风险** | 大模型直接生成SQL/查询，存在幻觉和安全风险 |
| **知识难复用** | ETL逻辑分散在脚本中，业务知识难以沉淀和复用 |

### 1.2 方案目标

引入**Palantir Ontology（本体论）**理念，对现有数据平台进行升级重构，实现：

| 目标 | 描述 |
|------|------|
| **语义统一** | 建立统一的本体模型，对业务实体、关系、操作进行结构化定义 |
| **关联穿透** | 引入图数据库，支撑百亿级数据的深度关联分析 |
| **AI可控** | 构建Action层，让AI在预定义边界内工作，降低幻觉风险 |
| **知识沉淀** | 将业务规则封装为可复用的Action，实现知识资产化 |
| **渐进演进** | 与现有架构平滑融合，分阶段演进 |

## 二、本体论方法论对比与创新

### 2.1 本体论 vs 传统数仓

| 对比维度 | 传统数仓模式 | 本体论模式 |
|----------|-------------|-----------|
| **核心关注** | 数据存储与ETL | 数据+语义+操作 |
| **建模方式** | 维度建模/范式建模 | 对象-关系-动作三元组 |
| **业务规则** | 散落在ETL脚本中 | 封装为可复用的Action |
| **AI集成** | RAG直接检索生成 | LLM调用预定义Action |
| **幻觉控制** | 弱，依赖Prompt工程 | 强，Action边界约束 |
| **知识复用** | 困难 | 天然支持 |

### 2.2 核心创新：Action驱动架构

传统方案：用户提问 → LLM理解 → 直接生成SQL/Cypher → 执行 → 返回结果

主要问题：可能生成错误查询、存在幻觉风险、不可审计、不可控。

本体论方案：用户提问 → LLM理解意图 → 映射到预定义Action → Action执行 → 结构化结果 → LLM生成答案

核心价值：Action经过测试验证，支持参数校验与权限检查，具备完整审计日志，确保可控可信。

## 三、总体架构设计

### 3.1 本体论指导下的数据平台架构

平台整体采用“语义层 + Action层 + AI决策层”的分层架构：

| 层级 | 关键能力 | 说明 |
|------|---------|------|
| **业务应用层** | 产业链分析、风险穿透、精准招商、智能问答 | 面向业务场景输出应用能力 |
| **动态层（AI决策层）** | Graph RAG、报告生成、决策模拟、反馈学习 | 支持多Action编排与闭环优化 |
| **动力层（Action层）** | 图谱分析Action、数据查询Action、业务规则Action | 统一承载可复用的业务逻辑 |
| **语义层（本体模型层）** | Object/Link/Rule体系 | 定义对象、关系、属性与约束规则 |
| **数据存储层** | 图数据库、关系型数仓、向量数据库 | Galaxybase + MySQL + Milvus 组合 |
| **数据治理层** | 本体模型管理、质量管理、元数据管理、血缘管理 | 支撑标准化治理与可信管理 |
| **数据接入层** | 数据库/文件/API/爬虫/消息队列 | 多源统一接入、映射到本体模型 |
| **基础设施层** | Kubernetes、Spark/Flink、DolphinScheduler | 计算与调度能力支撑 |

### 3.2 与现有天蓬平台的关系

| 现有模块 | 本体论升级 | 变化说明 |
|----------|-----------|----------|
| 数据接入 | 增加本体映射 | 接入时即进行本体模型映射 |
| 数据存储 | 增加图数据库 | 关系数据同步写入图库 |
| 数据治理 | 升级为本体治理 | 基于本体模型进行治理 |
| 数据ETL | 增加图谱构建 | ETL同时完成图谱写入 |
| 数据服务 | 增加Action层 | API封装为Action |
| 数据分析 | 增加图分析 | 集成图算法能力 |

### 3.3 Action层设计

Action是对业务能力的**可执行封装**，用于承接LLM意图并在受控边界内执行。每个Action必须与本体模型绑定，确保“语义-数据-操作”一致。

**Action定义规范**：

| 规范要素 | 说明 | 示例 |
|----------|------|------|
| Action名称 | 唯一标识 | equity_penetration |
| 业务描述 | 面向业务的说明 | 企业股权穿透查询 |
| 输入参数 | 参数名/类型/约束 | enterprise_id: string, depth: 1-10 |
| 输出结构 | 结构化结果约定 | List&lt;节点/关系/路径&gt; |
| 本体绑定 | 对应Object/Link类型 | Enterprise、InvestRelation |
| 执行逻辑 | 查询/算法/规则 | 图查询模板 + 校验规则 |
| 权限与审计 | 权限校验与日志 | 角色校验 + 审计日志 |

**Action分类**：

| 分类 | 作用 | 示例 |
|------|------|------|
| 图谱分析Action | 深度关联分析 | 股权穿透、供应链路径、社区发现 |
| 数据查询Action | 结构化指标统计 | 企业画像查询、产业统计聚合 |
| 业务规则Action | 规则判断与评分 | 风险评分、异常检测、阈值判断 |

**Action示例（摘要）**：

| Action名称 | 输入 | 输出 | 说明 |
|-----------|------|------|------|
| equity_penetration | enterprise_id, depth | 关系路径列表 | 股权穿透路径分析 |
| supply_chain_trace | product_id, depth | 供应链路径 | 供应链上下游追溯 |
| risk_scoring | enterprise_id | 风险评分结果 | 多维指标加权评分 |

## 五、本体论核心框架

### 5.1 核心本体定义

采用 **"1层核心本体 + 6大子体系"** 的分层架构：

| 核心维度 | 定义 | 映射子体系 |
|----------|------|-----------|
| 产业概念维度 | 产业链知识的核心分类基准 | 概念体系 |
| 产业主体维度(Actor) | 参与产业链运行的组织/机构 | 实体体系-产业主体实体 |
| 产业要素维度(Object) | 支撑产业链运转的有形/无形资源 | 实体体系-产业要素实体 |
| 产业事件维度 | 触发产业链动态变化的行为 | 事件体系 |
| 知识溯源维度 | 产业知识的来源与可信度 | 文档体系 |
| 事实知识维度 | 知识的适用边界与场景约束 | 事实情境体系 |

### 5.2 核心约束规则

1. 所有子体系必须遵循**"产业-产品-技术"统一分类标准**
2. 实体体系严格区分**产业主体与产业要素**
3. 所有事实性陈述必须绑定**文档来源与情境约束**

## 六、数据库选型方案

### 6.1 多数据库协同架构（沿用现有）

| 数据库类型 | 选型 | 国产信创替代 | 本体论对应存储内容 |
|-----------|------|---------------|-------------------|
| **关系型数据库** | MySQL/达梦 | 人大金仓/达梦 | 系统配置、本体元数据定义、文档类型体系 |
| **分析型数据库** | MySQL | 人大金仓/达梦 | ODS/DW/DM层结构化数据 |
| **文档数据库** | MongoDB |  | 结构化文档存储（文档体系） |
| **搜索引擎** | ElasticSearch | Easysearch | 文档索引与全文检索（服务层） |
| **图数据库** | ArangoDB | Galaxybase | 产业知识图谱(实体+关系) |
| **向量数据库** | Milvus |  | 文档向量化、语义检索 |
| **对象存储** | MinIO |  | 原始文件存储（PDF/图片等） |
| **缓存数据库** | Redis | Tendis/Tair/TongRDS | 采集任务队列、热点缓存 |

**选型说明（MySQL vs Doris）**：当前已部署 MySQL，可满足中小规模的数仓建模与统计需求。随着数据量与查询复杂度提升，可切换为与现有数仓一致的 **Doris** 以获得更高的并行聚合性能与大规模分析能力。

### 6.2 国产信创图数据库方案（Galaxybase）

针对信创要求，推荐采用国产图数据库**创邻Galaxybase**作为ArangoDB的替代或补充方案：

| 对比维度 | ArangoDB | Galaxybase |
|---------|----------|------------|
| **产地** | 德国/开源 | 国产/商业 |
| **信创适配** | 需验证 | 完全适配信创环境 |
| **性能特点** | 多模型数据库，通用性强 | 专注图计算，万亿边级别高性能 |
| **图算法** | 基础图遍历 | 内置100+图算法（PageRank、社区发现等） |
| **适用场景** | 中小规模知识图谱 | 大规模产业链图谱分析 |

**推荐策略**：
- **信创项目**：优先采用Galaxybase
- **通用项目**：可继续使用ArangoDB，或根据图谱规模选择

### 6.3 本体论视角下的数据存储分配

| 本体子体系 | 存储引擎 | 存储内容 |
|-----------|---------|---------|
| 概念体系 | MySQL + 图数据库 | 产业-产品-技术统一分类字典、概念层级图 |
| 实体类型体系(主体) | MySQL + 图数据库 | 企业/机构主体表、主体实体节点 |
| 实体类型体系(要素) | MySQL + 图数据库 | 产品/技术实体表、要素实体节点 |
| 关系类型体系 | 图数据库 + MySQL | 关系边、关系事实表 |
| 事件类型体系 | MySQL + 图数据库 | 事件事实表、事件节点 |
| **文档类型体系** | MySQL | 文档类型定义、分类标准、元数据Schema |
| **文档体系** | MongoDB + MinIO + Milvus | 结构化文档集、原始文件、语义向量 |
| 文档检索服务 | ElasticSearch | 文档索引、全文检索（服务层） |
| 事实情境体系 | 图数据库 + MySQL | 陈述-语句-情境三层结构 |

> **注**：图数据库可根据项目需求选择ArangoDB或Galaxybase

## 七、本体论指导下的数据处理流程

### 7.1 数据接入层（增加本体标签）

#### 数据接入方式（沿用）

| 接入方式 | 工具 | 本体论增强 |
|----------|------|-----------|
| 公开数据采集 | 八爪鱼/Python | 采集时打上**文档类型体系**标签 |
| 外部数据接入 | API/文件导入 | 导入时标注**实体类型体系**分类 |
| 内部数据导入 | DataX | 关联**概念体系**产业分类 |
| 实时数据同步 | Flink CDC | 实时标注**事件类型体系**标签 |

#### 本体标签标注机制（新增）

数据接入时自动为每条记录添加本体标签，包含以下核心字段：

| 标签字段 | 说明 | 示例值 |
|---------|------|-------|
| `entity_type` | 实体类型分类 | actor/object/event |
| `industry_level` | 产业层级编码 | 新能源汽车→动力电池→电芯制造 |
| `tag_time` | 标注时间戳 | 2024-01-15 10:30:00 |
| `source_system` | 来源系统 | tianyancha/patent_db |

**必要性说明**：本体标签用于消除多源数据的语义歧义，确保同一实体在不同系统中可被统一识别；同时为后续关系抽取、知识融合与可信度评估提供标准化输入。

### 7.2 数据存储层（增加本体组织）

#### ODS层表命名规范（本体论指导）

按本体论六大子体系组织ODS层表命名：

| 本体分类 | 表名前缀 | 示例表名 |
|---------|---------|---------|
| 主体实体类 | `ods_actor_` | ods_actor_tianyancha_enterprise（企业主体） |
| 要素实体类 | `ods_object_` | ods_object_patent_global（技术要素-专利） |
| 事件类 | `ods_event_` | ods_event_operation_expansion（运营事件） |
| 文档类 | `ods_document_` | ods_document_research_report（研报文档） |

#### DW层维度模型设计要点

**产业维度表（dim_industry）**：对应本体论"产业层级"，包含产业ID、名称、层级（1-大类/2-赛道/3-环节/4-节点）、父产业ID、本体概念ID、价值链位置等字段。

**企业维度表（dim_enterprise）**：对应本体论"产业主体实体"，包含企业ID、名称、统一社会信用代码、主体类型、所属产业ID、本体主体ID等字段。

#### 事实表设计要点

**产业供需关系事实表（fact_supply_demand）**：记录供应商ID、需求方ID、产品ID、供应比例，并关联来源文档ID和可信度等级，支持知识溯源。

**产业事件事实表（fact_industry_event）**：记录事件类型（运营/技术/政策/市场）、关联主体、所属产业、来源文档和可信度。

### 7.3 数据治理层（沿用现有，增加本体标准）

#### 数据治理流程（本体论融入）

| 流程阶段 | 核心操作 | 本体论增强 |
|---------|---------|----------|
| 数据接入 | 多源采集、格式转换、数据校验 | 标注来源系统、数据类型 |
| 本体标注 | 本体分类标签、概念映射 | 实体类型识别、可信度评估 |
| 数据清洗 | 规则清洗、缺失补全、重复去除 | 概念统一映射 |
| 语义融合 | 实体对齐、关系抽取、知识融合 | 本体约束验证 |
| 质量监控 | 语义一致性检测、完整性检测 | 本体规则校验 |

**现有流程保持不变**：数睿ETL + Spark数据处理 + DolphinScheduler调度

**本体论增强点**：本体标签标注 + 概念体系映射 + 语义一致性校验

**必要性说明**：本体标准用于统一字段口径与关系语义，避免同名不同义导致的错误统计；同时为数据治理提供可验证的规则边界，使质量监控具备可量化的判定依据。

### 7.4 知识图谱存储（ArangoDB）

#### 图谱Schema设计

**节点集合**：

| 集合名 | 存储内容 | 核心属性 |
|-------|---------|--------|
| actors | 产业主体节点 | 名称、类型、产业层级、价值链角色 |
| objects | 产业要素节点 | 产品/技术名称、分类、属性 |
| events | 产业事件节点 | 事件类型、时间、关联主体 |
| concepts | 概念节点 | 概念名称、层级、定义 |

**关系类型**：

| 关系类型 | 说明 | 示例 |
|---------|------|-----|
| supply | 供应关系 | 供应商→采购商 |
| tech_enable | 技术赋能 | 技术→产品 |
| event_participate | 事件参与 | 主体→事件 |
| belong_to | 属于关系 | 实体→产业层级 |

#### 图谱节点示例

以企业主体节点为例，包含以下核心属性：
- **_key**：唯一标识（如 ent_001）
- **name**：企业名称（如 宁德时代新能源科技股份有限公司）
- **actor_type**：主体类型（producer/supplier/consumer）
- **ontology_labels**：本体标签，包含产业层级、价值链角色等

关系边包含来源文档ID和可信度等约束上下文，支持知识溯源。

## 九、本体元数据管理

### 9.1 本体元数据表设计

**本体概念定义表（meta_ontology_concept）**：存储产业-产品-技术统一分类体系，包含概念ID、名称、类型、层级、父概念ID、定义、同义词等字段。

**本体实体类型定义表（meta_ontology_entity_type）**：定义实体类型元数据，区分actor/object两大类，包含必填属性、绑定概念类型等。

**本体关系类型定义表（meta_ontology_relation_type）**：定义关系类型元数据，包含源实体类型、目标实体类型、语义描述等约束。

## 十一、总结

本方案通过**本体论语义层**将公司现有数据平台的各个模块串联起来：

1. **数据接入**：通过本体标签标注，在数据进入时即赋予语义分类
2. **数据存储**：按本体论六大子体系组织数据，MySQL存结构化、ArangoDB存图谱、ES存文档
3. **数据治理**：增加语义一致性校验，确保数据符合本体约束
4. **数据分析**：基于本体关系进行产业链分析、路径分析
5. **数据服务**：提供结构化查询、图谱查询、语义检索等多种API

**核心价值**：在不大幅改动现有稳定流程的前提下，通过本体论框架实现**多源数据的语义统一**，为上层应用提供**统一的产业知识语义体系**。
